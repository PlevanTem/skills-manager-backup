# 知识图谱 Skill 使用说明

## 一、功能介绍

### 1.1 Skill 概述

**知识图谱 Skill** 是一个端到端的知识图谱建设、维护与质量管理引擎。它能从业务文档、代码仓库、类图等多种知识源中自动提取实体和关系，构建全连通的结构化知识图谱，并通过 BFS 验证确保零孤立节点。

**YAML 主管道**输出五层知识架构：
- **entities** — 概念层：实体（核心概念/枚举/事件/角色/流程）
- **relations** — 结构层：关系（包含/归属/依赖/触发/引用等 12 种类型）
- **rules** — 规则层：业务规则（验证/约束/计算/权限/流程控制）— 条件产出，需有需求文档或用例规约作为知识源
- **flows** — 流程层：业务流程（步骤化的流程定义）— 条件产出，需有需求文档或用例规约作为知识源
- **glossary** — 翻译层：术语表（代码术语→业务概念的翻译字典）— 条件产出，需有代码作为知识源

所有 Stage（提取→生成→自检→评分）、验证脚本和可视化工具均围绕这五层运转；rules/flows/glossary 层在缺少对应知识源时自动跳过。

### 1.2 核心能力

| 能力 | 说明 |
|------|------|
| 多源知识提取 | 支持纯文档、文档+类图、文档+代码、纯代码四种知识源类型 |
| 5 大执行模式 | 全量构建、增量更新、质量自检、评分、知识查询 |
| BFS 全连通验证 | 自动检测孤立节点和断连子图，确保图谱单连通 |
| 三维评分体系 | KG 质量(40%) + 消费质量(40%) + 维护质量(20%)，共 100 分 |
| 版本化管理 | 每次生成输出到独立版本文件夹，不覆盖历史版本 |
| 增量更新 | 变更检测→影响分析→增量提取→合并→冲突解决→验证 |
| 五层知识架构 | entities（概念）+ relations（结构）+ rules（规则）+ flows（流程）+ glossary（翻译）|
| 多轮迭代收敛 | 自动迭代直至覆盖率=100%、连通率=100%、质量分≥80 |
| 执行保护 | 检查点持久化、中断恢复、大规模分批处理、阶段内落盘 |

### 1.3 适用场景

**适用于：**
- 从业务文档中提取实体和关系，构建结构化知识图谱
- 从代码仓库中分析业务概念和调用关系
- 对已有知识图谱进行质量检查和评分
- 增量更新已有知识图谱（文件变更后）
- 查询图谱中的业务知识

**不适用于：**
- 纯数据字典整理 → 请使用名词库工具
- 单个 API 文档编写 → 请使用 `gen-contract` 契约工具
- 流程图绘制 → 请使用 `drawio-diagrams` Skill
- 领域概念建模（含聚合/泛化等） → 请使用 `domain-modeling` Skill

### 1.4 文档职责说明

- `SKILL.md` 是运行规范的单一事实来源：模式路由、Stage 定义、输出文件名、脚本入口和资源索引都以它为准。
- `USAGE.md` 是上手说明和常用信息镜像：保留示例对话、环境要求、常用命令和文件结构速查。
- `CHANGELOG.md` 负责完整版本历史；`evaluation-report.md` 只记录某次评审结论。

**同步约定**：
- 如果工作流、输出文件名、脚本入口或资源索引发生变化，先改 `SKILL.md`
- 同一提交内同步检查本文件的 `2.2`、`3.1`、`5.2`、`5.3`、`5.4`

## 二、使用方法

### 2.1 触发方式

在任意支持技能路由、系统提示注入或等价能力的大模型对话环境中，当用户使用以下表达时应触发此 Skill：

| 类别 | 触发词示例 |
|------|----------|
| 构建图谱 | "知识图谱"、"生成知识图谱"、"业务概念关系"、"实体关系图" |
| 业务分析 | "概念网络"、"名词关系梳理"、"业务理解"、"代码业务分析" |
| 技术术语 | "ontology"、"GraphRAG"、"KG" |

### 2.2 五大执行模式

Skill 根据用户意图自动选择模式（默认 `full`）：

#### 模式一：全量构建（full）

**触发**：用户提供知识源并要求构建知识图谱

**流程**：Stage 1(规划) → Stage 2(提取) → Stage 3(生成) → Stage 4(自检) → Stage 5(评分)

**示例对话**：
```
用户：帮我基于 avatar/领域建模/ 目录下的文档生成知识图谱
AI：[Stage 1] 盘点知识源、划分子域、定义能力问题、生成执行计划
    [Stage 2] 逐文件提取实体+关系+规则
    [Stage 3] 去重规范化 + BFS 连通验证 + 生成输出文件
    [Stage 4] 质量自检（覆盖率/连通率/引用正确性）
    [Stage 5] 三维评分
```

#### 模式二：增量更新（incremental）

**触发**：已有知识图谱，文件变更后需要更新

**流程**：Stage 6(增量) → Stage 2 → Stage 3 → Stage 4 → Stage 5

**特性**：
- 更新前自动备份（保留最近 3 个版本）
- `.kg-lock` 文件防并发冲突
- 变更检测→影响分析→增量提取→合并→冲突解决

#### 模式三：质量自检（validate）

**触发**：说"检查图谱质量"/"自检"

**流程**：仅执行 Stage 4

**检查项**：

| 检查项 | 通过标准 |
|-------|---------|
| 用户知识源覆盖率 | = 100% |
| BFS 全连通 | = 100%（单连通分量） |
| 关系引用正确性 | 0 无效引用 |
| 枚举归属完整性 | 每个枚举实体 ≥ 1 条归属关系 |
| 跨域桥接完整性 | 桥接检查清单每项至少 1 条边 |
| 能力问题(P0) | 100% 可回答 |

#### 模式四：评分（score）

**触发**：说"对图谱打分"/"评分"

**流程**：仅执行 Stage 5

**三维评分体系**：

| 维度 | 权重 | 核心指标 |
|------|------|---------|
| KG 本身质量 | 40% | 准确性(25%)、完整性(25%)、一致性(20%)、连通性(15%)、语义丰富度(15%) |
| 消费质量 | 40% | 能力问题覆盖率(30%)、多跳推理(25%)、路径多样性(20%)、可理解性(15%)、Token效率(10%) |
| 维护质量 | 20% | 溯源完整性(30%)、Schema规范性(25%)、增量友好度(20%)、版本管理(15%)、文档化(10%) |

**评分等级**：

| 等级 | 分数 | 含义 |
|------|------|------|
| S | ≥ 90 | 优秀，可直接用于生产 |
| A | 80-89 | 良好，需少量补充 |
| B | 70-79 | 合格，需迭代优化 |
| C | 60-69 | 不合格，需重大修改 |
| D | < 60 | 严重不合格，需重建 |

#### 模式五：知识查询（query）

**触发**：说"查询图谱中的..."/"XX 和 YY 是什么关系"

**行为**：直接读取 KG 数据文件回答问题，无需重新构建。

## 三、使用步骤

### 3.1 全量构建流程（6 个 Stage）

#### Stage 1：规划（Planner）

**目标**：盘点知识源、划分子域、制定执行计划

**操作**：
1. 扫描用户指定的目录/文件，逐文件统计数据条目数
2. **知识源分类**：按文件内容特征自动识别领域模型/需求文档/用例规约/代码，标注 `contributes_to`（entities/relations/rules/flows/glossary）和输入完整度评估
3. 识别结构化数据源链接（如 XWatt 类图 URL）
4. 划分子域边界，创建版本输出目录（如 `v7/`）
5. 定义 ≥ 20 个能力问题（P0/P1/P2 三级优先级）
6. 生成执行计划：知识源 100% 覆盖清单 + 补充数据源清单

**输出物**：`execution-plan.md` + `competency-questions.yaml`

#### Stage 2：提取（Extractor）

**目标**：从知识源中提取实体、关系、规则、流程

**提取策略**（按知识源类型自动选择）：

| 知识源特征 | 骨架提取 | 补充连接手段 |
|-----------|---------|-------------|
| 纯文档 | 逐文件提取实体+关系+枚举 | 文档中的 UML 文本/关系段落 |
| 文档+类图链接 | 文档提取枚举/配置 | 调用类图结构化接口获取结构化边 |
| 文档+代码 | 文档提取概念 | 代码引用/外键/调用链 |
| 纯代码 | 代码搜索/文件枚举 | 依赖/调用关系自动提取 |

**三段并行提取**（根据 Stage 1 知识源分类结果驱动）：
- **段 A**（实体+关系）：领域模型/类图 → 提取实体、关系、枚举
- **段 B**（规则+流程）：需求文档/用例规约 → 提取业务规则、业务流程
- **段 C**（术语+映射）：代码 → 提取术语表、代码映射

**并行任务**：
1. 知识源扫描（必选）
2. 名词查询（有 xnoun 或等价名词库接口时并行）
3. 类图结构化提取（有类图 URL 时并行）
4. 代码扫描（有代码时并行）

**输出物**：`kg-triples-raw.yaml`

#### Stage 3：生成（Generator）

**目标**：去重规范化、BFS 连通验证、生成最终输出

**操作**：
1. 实体/关系去重规范化（ID 格式 `E_{DOMAIN}_{NAME}`）
2. BFS 全连通验证 → 补桥 → 重复直至 100%
3. 社区检测（按关系密度识别子域社区）
4. 合并输出

**输出物**：

**主输出（YAML，机器可读）**：

| 文件 | 内容 |
|------|------|
| `kg-entities.yaml` | 全量实体，结构化 YAML，供脚本和后续流水线直接消费 |
| `kg-relations.yaml` | 全量关系，结构化 YAML，供脚本和后续流水线直接消费 |
| `kg-rules.yaml` | 业务规则，结构化 YAML（条件产出，需有需求文档/用例） |
| `kg-flows.yaml` | 业务流程，结构化 YAML（条件产出，需有需求文档/用例） |
| `kg-glossary.yaml` | 术语表，结构化 YAML（条件产出，需有代码） |

**衍生输出（从 YAML 自动生成）**：

| 文件 | 内容 |
|------|------|
| `kg-entities.md` | 全量实体的人类可读 Markdown 表格 |
| `kg-relations.md` | 全量关系的人类可读 Markdown 表格 |
| `kg-rules.md` | 业务规则的人类可读 Markdown 表格 |
| `kg-flows.md` | 业务流程的人类可读 Markdown 表格 |
| `kg-glossary.md` | 术语表的人类可读 Markdown 表格 |
| `knowledge-graph.html` | 可交互可视化图谱（必选） |
| `kg-unconnected.md` | 孤立节点清单 |
| `kg-entity-mapping.md` | 多源归并映射 |
| `kg-synonym-groups.md` | 同义概念归类清单 |

#### Stage 4：自检（Validator）

**目标**：验证图谱质量，确保各项指标达标

**检查项**：用户知识源覆盖率、BFS 全连通、关系引用正确性、枚举归属完整性、跨域桥接完整性、能力问题可回答率、规则层校验（involvedEntities 引用、condition 非空、type 合法）、流程层校验（steps.ruleRef/entityRef 引用）、术语层校验（entityRef 引用、term 唯一）、跨层引用正确率

**输出物**：`kg-validation.yaml`

#### Stage 5：评分（Scorer）

**目标**：三维综合评分

**输出物**：`kg-score.yaml`

#### Stage 6：增量更新（Guardian）

**目标**：变更后增量更新图谱

**流程**：变更检测 → 影响分析 → 增量提取 → 合并更新 → 冲突解决 → 增量验证 → 记录日志

### 3.2 快速开始示例

```
用户：帮我基于以下文档生成知识图谱：avatar/领域建模/交易领域模型.md

AI：[Stage 1 — 规划]
    - 知识源：1 个文件（交易领域模型.md）
    - 子域：C2B 交易域
    - 能力问题：20 个（含"交易订单包含哪些子单？"等）
    - 执行计划已输出到 execution-plan.md

    确认后开始提取？

用户：确认

AI：[Stage 2 — 提取] 提取到 25 个实体、38 条关系、5 条业务规则
    [Stage 3 — 生成] BFS 连通率 100%，已输出 kg-entities.yaml、kg-relations.yaml、knowledge-graph.html 等文件
    [Stage 4 — 自检] 覆盖率 100%，连通率 100%，0 无效引用 → PASS
    [Stage 5 — 评分] 综合分 85 分（A 级），KG质量 88 / 消费质量 83 / 维护质量 82
```

### 3.3 确认策略

Skill 根据图谱规模自动决定是否需要用户确认：

| 规模 | 行为 |
|------|------|
| ≤ 5 个实体 | 跳过确认，直接生成 |
| 6-15 个实体 | 精简清单确认 |
| > 15 个实体 | 完整清单，等用户确认后继续 |

## 四、注意事项

### 4.1 铁律（必须遵守）

| 铁律 | 说明 |
|------|------|
| 忠于原文 | 禁止捏造概念，无据可查的标注「待确认」 |
| 先查后问 | 先用外部知识接口、全文搜索和文件读取能力自行获取信息，只问用户才知道的事 |
| AI-first 表达 | description 写清「是什么 + 为什么 + 角色」，AI 无需额外上下文即可理解 |
| 本体化建模 | 业务概念建模为具有独立身份、属性和关系的本体对象，而非扁平数据字典 |
| 名词库优先 | 名词以 xnoun 或等价名词库接口的查询结果为标准定义 |
| 尊重用户边界 | 用户指定知识源范围时，严格在该范围内提取 |
| 全连通网络 | 最终图谱必须是单连通分量，不允许孤立节点或断连子图 |
| 版本化输出 | 每次生成输出到独立版本文件夹，不覆盖历史 |

### 4.2 实体与关系判定规则

**实体 vs 属性**：

```
名词 N →
  有独立 ID？ → 实体
  有独立生命周期？ → 实体
  被 ≥ 2 个概念引用？ → 实体
  在代码中有独立的表/类？ → 实体
  以上都否 → 属性（挂到最近实体下）
```

**实体类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| `core` | 有独立 ID + 生命周期的核心概念 | 订单、商户、账户 |
| `enum` | 有限选项的枚举值 | 订单状态、支付方式 |
| `event` | 动作产物/业务事件 | 退款记录、审批单 |
| `role` | 角色 | 商户管理员、审核人 |
| `process` | 流程 | 开户流程、退款流程 |

**关系类型**（12 种）：

| 类型 | 中文 | 信号词 |
|------|------|--------|
| `contains` | 包含 | 包含/包括/由...组成/下设 |
| `belongs_to` | 属于 | 属于/隶属于 |
| `depends_on` | 依赖 | 依赖/基于/需要/前提是 |
| `associates` | 关联 | 关联/对应/绑定 |
| `generalizes` | 泛化 | 是一种/分为 |
| `triggers` | 触发 | 触发/引发/导致 |
| `produces` | 产生 | 生成/产生/创建/输出 |
| `references` | 引用 | 引用/使用/读取/查询 |
| `manages` | 管理 | 管理/维护/审批 |
| `transforms` | 转化 | 转化为/变成 |
| `precedes` | 前置 | 先于/完成后才能 |
| `constrains` | 约束 | 限制/约束/必须满足 |

### 4.3 多源冲突处理

当同一概念来自多个知识源时，按以下优先级处理：

```
xnoun 名词库 > 知识源文档 > 补充数据源 > 用户口述
```

同一概念不同名称时，以知识源名称为准，所有变体记录到 `kg-entity-mapping.md`。

### 4.4 枚举值处理

- 每个枚举值必须通过 `枚举归属` 关系连接到父类型实体
- 树形枚举使用 `层级归属` 关系
- 未连接的枚举值会导致 BFS 验证不通过

### 4.5 大规模图谱注意事项

| 条件 | 触发保护机制 |
|------|------------|
| 知识源 ≥ 10 个文件 | 启用检查点持久化 |
| 实体 ≥ 50 个 | 启用分批提取 |
| ≥ 3 个子域 | 按子域分批，每批工具调用 ≤ 15 次 |
| 实体 > 100 或关系 > 200 | Stage 3/4 每完成 1 个子域或每新增 50 个实体/关系，刷新一次草稿文件并写入 `kg-progress.md` |
| 实体 ≥ 500 个 | 启用分段保护，按子域分批生成并优先维护进度摘要 |

### 4.6 常见问题与解法

| 问题 | 根因 | 解法 |
|------|------|------|
| BFS 发现大量孤立节点 | 枚举值未连到父类型 | 检查每个枚举是否有 `枚举归属` 边 |
| 两个子域完全断连 | 缺少跨域桥接边 | 查桥接检查清单逐项补边 |
| 类图文本提取的边比实际少 | 人工文档遗漏 | 用结构化数据源（XWatt/代码外键）补充 |
| 同一概念重复为两个实体 | 多源命名不一致 | 归并为一个，记录到映射文件 |
| 生成脚本太大上下文溢出 | 数据量超 500 实体 | 启用分段保护，按子域分批生成 |

### 4.7 收敛条件

多轮迭代时，全部满足以下条件方可停止：

- 用户知识源覆盖率 = 100%
- BFS 连通率 = 100%（无孤立节点）
- 关系引用正确率 = 100%（0 无效引用）
- 质量分 ≥ 80

连续 2 轮提升 < 2 分 → 收敛停止，最多 20 轮。

## 五、系统要求

### 5.1 运行环境

| 项目 | 要求 |
|------|------|
| 宿主环境 | 任意支持文件读取、全文搜索、命令执行和多轮协作的大模型宿主环境 |
| Python | 3.x（用于运行自检脚本和工具脚本；YAML 主流程建议安装 `PyYAML`） |
| 外部接口（可选） | `xnoun` 或等价名词库接口 — 名词查询 |
| 外部接口（可选） | `xwatt` 或等价类图接口 — XWatt 类图结构化提取 |
| 浏览器（可选） | 任意现代浏览器 — 打开 `knowledge-graph.html` 进行交互查看 |

### 5.2 关键文件结构

主要结构如下。文中 `<skill-root>` 表示当前 Skill 根目录，可替换为相对路径、工作区路径或宿主环境提供的等价变量：

```text
knowledge-graph/
```

### 5.3 工具脚本

**图谱自检**：
```bash
python3 <skill-root>/scripts/kg_validate.py <entities.yaml> <relations.yaml> [rules.yaml] [flows.yaml] [glossary.yaml]
```

检查项：实体必填属性完整性、关系引用有效性、孤立节点检测、重复 ID 检测、继承关系环检测、规则层校验、流程层校验、术语层校验。缺失的可选文件会跳过对应层校验。

**HTML 可视化生成**：
```bash
python3 <skill-root>/scripts/kg_to_html.py <entities.yaml> <relations.yaml> [output.html]
```

说明：默认生成 `knowledge-graph.html`；脚本依赖同目录下的 `kg_html_template.html` 页面模板。

**导出为 draw.io**：
```bash
python3 <skill-root>/scripts/kg_to_drawio.py <kg.json> <output.drawio>
```

说明：输入需为符合 `references/kg_schema.md` 的 schema-compatible JSON，而不是 Stage 3 的 YAML 主输出。

**导出为 Markdown 上下文**：
```bash
python3 <skill-root>/scripts/kg_to_markdown.py <kg.json> <output.md>
```

说明：输入同样为 schema-compatible JSON，适合把完整知识图谱转成 AI 注入上下文。
