# knowledge-graph

> 端到端知识图谱建设、自检、评分、维护引擎，五层结构化输出

---

## 基本信息

| 字段 | 内容 |
|------|------|
| **作者** | 业务架构组 |
| **适用场景** | 全量构建知识图谱；文件变更后增量更新；基于名词列表扩展已有图谱；检查现有图谱质量；对图谱打分；查询图谱中的知识 |
| **不适用场景** | 纯数据字典整理（用名词库）；单个 API 文档编写（用契约工具）；流程图绘制（用 drawio-diagrams）；领域建模（用 domain-modeling） |
| **目标用户** | 业务架构师、知识工程师、需要从多源文档/代码构建结构化知识体系的团队 |

## 触发描述

用户提出以下需求时，Agent 应触发本 Skill：

- "知识图谱""生成知识图谱""构建 KG" — 全量构建模式
- "更新图谱""增量更新" — 增量更新模式
- "名词扩展""扩展实体" — 名词扩展模式
- "检查图谱质量""验证图谱" — 自检模式
- "图谱打分""评分" — 评分模式
- "查一下 XX 和 YY 的关系" — 查询模式

触发词：知识图谱、生成知识图谱、业务概念关系、实体关系图、概念网络、名词关系梳理、业务理解、代码业务分析、ontology、GraphRAG、KG。

## 执行步骤

### 6 个 Stage 流水线

| Stage | 名称 | 核心操作 |
|-------|------|---------|
| 1 | 规划（Planner） | 盘点知识源 → 知识源分类 → 领域划分 → 定义能力问题 → 生成执行计划 |
| 2 | 提取（Extractor） | 三段并行提取：段 A（实体+关系骨架）、段 B（规则+流程）、段 C（术语+映射） |
| 3 | 生成（Generator） | 多域合并 → BFS 全连通验证 → ID 互引校验 → 社区检测 → 五层 YAML 输出 → HTML 可视化 |
| 4 | 自检（Validator） | 结构层/规则层/流程层/术语层/综合检查 → 四维评估（noun_extension 模式） |
| 5 | 评分（Scorer） | KG 质量(40%) + 消费质量(40%) + 维护质量(20%) → S/A/B/C/D 等级 |
| 6 | 增量更新（Guardian） | 变更检测 → 影响分析 → 增量提取 → 合并更新 → 冲突解决 |

### 6 种执行模式

`full`（全量）、`incremental`（增量）、`noun_extension`（名词扩展）、`validate`（自检）、`score`（评分）、`query`（查询）。

## 关键判断点

| 判断点 | 决策规则 | 容易出错的原因 |
|--------|---------|---------------|
| 实体 vs 属性 | 有独立 ID / 独立生命周期 / 被多个概念引用 → 实体，否则 → 属性 | 将本应是实体的概念降级为属性（如"地址"应有独立身份） |
| BFS 全连通验证 | `full`/`incremental` 模式要求 100% 连通；`noun_extension` 骨架 100% 连通 | 枚举值未连到父类型、跨域缺少桥接边 |
| 同名实体唯一 | 同一概念只允许一个权威实体，其他域通过 `depends_on` 引用 | 下游域创建"引用实体"影子副本（铁律 9 禁止） |
| 桥接关系类型保真 | 仅"同一实体"转 `depends_on`，其他类型保留原 relation_type | 合并时一刀切转为 `depends_on`（AP009 反模式） |
| 规则类型判定 | 校验→validation / 约束→constraint / 计算→calculation / 权限→permission / 流程控制→flow_control | 混淆"必须"是 validation 还是 constraint |
| 名词扩展阈值 | 融合分 ≥ 0.15 才建立关系，高频实体 Top-5% 软降权 | 阈值太低导致噪声关系（AP008） |

## 输出要求

### 五层 YAML 主管道输出

| 层 | 文件 | 内容 |
|----|------|------|
| 概念层 | `kg-entities.yaml` | 业务概念 + 属性 + 代码映射 + 状态转换 |
| 结构层 | `kg-relations.yaml` | 概念间关系 + 基数 + 数据路径 |
| 规则层 | `kg-rules.yaml` | 业务约束/校验/计算/权限规则 |
| 流程层 | `kg-flows.yaml` | 业务流程步骤 + 规则引用 |
| 翻译层 | `kg-glossary.yaml` | 代码符号 → 业务概念映射 |

**衍生输出**：对应 `.md` 文件 + `knowledge-graph.html`（可交互可视化）+ `kg-unconnected.md` + `kg-entity-mapping.md` + `kg-synonym-groups.md`

## 验证方式

- **Stage 4 自检**：结构层 6 项检查 + 规则层 3 项 + 流程层 3 项 + 术语层 2 项 + 综合检查 2 项
- **BFS 全连通验证**：构建邻接表 → BFS → 对比可达集（脚本：`kg_validate.py`）
- **ID 互引校验**：rules→entities、flows→rules、flows→entities、glossary→entities
- **四维质量评估**（noun_extension）：P0 稀疏度 / P1 Judge Precision / P2 加权 Precision / P3 AUC-PR
- **Stage 5 评分**：三维评分（KG 质量 + 消费质量 + 维护质量），S/A/B/C/D 等级
- **使用反馈收集**：4 维度结构化反馈表

---

## 多模型兼容能力

- **核心流程模型无关**：6 Stage 流程依赖文件读写和 YAML 处理，不依赖特定模型能力
- **名词扩展模式受限**：三信号融合算法（TF-IDF + Jaccard + mention_boost）需要 `python3.9+` + `scikit-learn` + `jieba` + `numpy`，若环境不支持则该模式不可用
- **规模降级**：实体 < 50 全量处理；50-200 按模块筛选；> 200 最小子集（<30 个）
- **分批执行**：Stage 2 按子域分批，每批工具调用 ≤ 15 次
- **上下文阈值保护**：单轮接近 15 次工具调用时先写进度文件再继续

## 使用案例

**案例：微信支付退款域知识图谱构建**

> 用户输入："帮我构建退款域的知识图谱"
>
> 执行路径（full 模式）：
> 1. Stage 1 规划 — 扫描退款域文档目录，分类知识源：领域模型文档（基准）、需求文档（辅助）、代码（辅助），定义 25 个能力问题
> 2. Stage 2 提取 — 段 A 从类图提取"退款单、退款申请、退款审核"等实体；段 B 从需求文档提取"退款金额不得超过原支付金额"等规则；段 C 从代码提取 `RefundOrder` → `退款单` 术语映射
> 3. Stage 3 生成 — 去重消歧 → BFS 验证（发现退款原因枚举未连到退款单）→ 补边 → 输出五层 YAML + HTML 可视化
> 4. Stage 4 自检 — 覆盖率 100%、BFS 连通率 100%、同名实体 0 重名、规则引用全部有效
> 5. Stage 5 评分 — KG 质量 85 + 消费质量 82 + 维护质量 88 = 总分 84（A 级）
>
> 产出：`v7/` 目录下五层 YAML + `knowledge-graph.html`（ECharts 力导向图，按退款/审核/结算三域着色）
