# 运行期注意事项

这份文档关注的是“评测体系跑起来以后”的运行问题，而不是指标设计本身。

## 一、成本控制

本地评测架构跑通后，最常见的问题不是“能不能跑”，而是“跑起来成本是否可控”。

建议至少和用户讨论：

- 是全量跑，还是抽样跑
- batch 大小是多少
- judge 是同步跑还是异步跑
- score 是每次都回写，还是先汇总后回写

默认建议：

- 第一版先用小样本和代表性 fixture 跑通
- 稳定后再扩大到批量评测
- 高成本 judge 不要一开始就全量打生产 trace

## 二、PII 与敏感信息

payload 发给外部 judge 前，必须先考虑脱敏。

重点关注：

- 用户标识
- 业务内部 URL
- token、密钥、cookie
- 日志中的敏感字段
- 原始代码路径或私有仓库信息

默认建议：

- 在 payload 生成层就做脱敏
- 脱敏规则写进 spec
- judge 只看评测所需的最小字段

## 三、版本管理

以下内容都应单独版本化：

- judge prompt
- rubric
- score schema
- 聚合规则
- fallback 规则

推荐写进 score metadata 的内容：

- evaluator model
- rubric version
- prompt version
- score schema version
- aggregation version

但要注意：这些信息不能只在事后写进 metadata，运行前也必须先确认。

至少要先问清楚：

- 默认 judge 模型是什么
- 是否存在大上下文兜底模型
- 触发切换条件是什么
- 超时阈值是什么，例如多少分钟没有返回算超时
- 超时后是重试、切兜底模型、降并发，还是直接失败
- 如果没有兜底模型，用户接受哪种降级策略

## 四、模型与平台配置门禁

在真正跑评测前，下面这些配置都必须被用户、代码或明确配置直接证明：

- Langfuse project / space 对应关系
- base URL（如适用）
- 鉴权方式
- 密钥是否已配置
- `agent_name` 或等价筛选字段
- trace 过滤维度
- 默认 judge 模型
- 大上下文兜底模型或明确替代策略

如果上述任一项还不确定，就不能把当前链路当成“可直接运行”。

无兜底模型时，必须让用户明确选择：

1. 跳过超长样本
2. 增强压缩或摘要
3. 改用别的 judge 路径
4. 先只做 reduced-scope 版本

## 五、风险类指标的方向

不是所有指标都和主分方向一致。

例如：

- `Correctness`、`Relevance`、`Helpfulness` 往往是越高越好
- `Hallucination`、`Toxicity` 往往是风险越高分越高

因此在做综合分之前，必须先和用户确认：

- 这些风险指标是单独展示
- 还是做方向反转后再参与聚合
- 还是作为门禁，不进平均分

默认建议：

- 风险类指标优先单独展示
- 真要进综合分，必须把方向变换写进 spec 和 metadata

## 六、采样与基线

如果要持续跑评测，就要定义基线。

建议至少明确：

- 基线是哪个版本
- 用哪批样本做对比
- 多久更新一次基线

如果没有稳定基线，就不要过早宣称“分数变好了”。

## 七、重试与幂等

本地链路里常见失败点：

- Langfuse 拉 trace 失败
- judge 输出解析失败
- score 回写失败

建议：

- 每一步都能单独重试
- score 回写前有稳定主键或去重策略
- 回写失败时先落本地结果文件，不要直接丢失

## 八、运行日志最小覆盖面

如果没有足够日志，很多“评测不合理”最后都会变成猜谜。

至少覆盖：

- sample / trace 是怎么被选中的
- payload 取了哪些字段，缺了哪些字段
- 哪些字段触发了压缩、裁剪或兜底模型
- judge 请求用了哪个模型、哪个 prompt / rubric 版本
- judge 响应是否解析成功，失败时失败在哪
- score / report 最终输出到了哪里

日志不需要暴露全部原文，但至少要能让人复盘单条样本的关键链路。

## 九、样本抽检与结果复盘

第一版跑通后，不要只看均分或总表。

建议至少抽检 3 到 5 条代表性样本：

- 正常成功样本
- 压缩命中样本
- 特殊标签样本
- 明显失败或异常样本

重点看：

- judge reason 是否和 score 一致
- payload 是否真在支撑你设计的指标
- 标签边界是否被正确触发
- 是否需要调整 payload、rubric、聚合方式

## 十、完成前整体 review

在宣称“这套链路可运行”前，至少检查一次：

- 是否真的能从 trace / sample 走到 score / report
- 是否存在只能单独运行某一步、但串不起来的情况
- 是否已经明确本地与测试环境的执行方式
- 如果有接口，是否已经明确测试接口与调用方式
- 如果没有接口，是否已经明确内部 runner / 脚本入口

如果环境里可用，建议在收尾前再走一次等价于：

- `verification-before-completion`
- `requesting-code-review`

## 十一、第一版默认运行策略

如果用户没有特别要求，默认建议：

1. 小样本
2. 代表性 trace
3. 主分项 + breakdown
4. 本地先出结果文件
5. 确认稳定后再回写 Langfuse
