# E2E 指标参考

当用户已经在现有评测平台上做 E2E 评测时，不要默认从零自定义全部指标。

先检查平台里已有的指标、evaluator 模板或团队现成 score 名，然后再决定：

- 哪些直接复用
- 哪些需要补充
- 是否要做综合分

## 使用原则

### 先复用，再补缺口

优先复用满足以下条件的指标：

- 语义稳定
- 团队已经熟悉
- 能和当前 agent 场景对应上
- 在历史上已经有可比数据

只有当以下情况出现时，才建议新增自定义指标：

- 现成指标语义和业务需求不一致
- 现成指标不能覆盖当前 agent 的关键流程特色或关键风险
- 需要补充某些场景特有维度，比如 RAG 或 transfer

如需查看更完整的指标 prompt 样例、输入变量和输出格式，继续参考：

- [指标 Prompt 参考附录](langfuse-metric-prompts.md)

## 常见 E2E 指标方向

下面这些更适合作为“基础指标族”或 prompt 参考来源，不建议默认原封不动照搬成第一版指标名。

更推荐先问：

- 当前 agent 最关键的错误模式是什么
- 当前 agent 最重要的成功条件是什么
- 哪些风险如果漏掉，会直接让答案看起来还行、但实际不可用

再从这些基础方向里裁出更细的指标。

| 基础指标族 | 更适合拆成什么细粒度方向 |
|---|---|
| Correctness / Answer Correctness | 关键事实是否成立、关键结论是否错误、关键结果是否达成 |
| Relevance / Answer Relevance | 是否真正回应用户目标、是否回答了错的问题 |
| Faithfulness / Groundedness | 是否有幻觉、是否越过可见证据、是否和上下文矛盾 |
| Goal Accuracy | 用户目标是否完成、结果是否达到验收条件 |
| Helpfulness | 是否给出可执行下一步、是否对用户有行动价值 |
| Conciseness | 是否冗余、是否影响执行理解 |
| Toxicity / Safety | 是否触发风险内容或越界表达 |

如果是检索或上下文强相关场景，再从下面这些方向补专项指标：

| 基础指标族 | 更适合拆成什么细粒度方向 |
|---|---|
| Context Precision | 给到的上下文里真正有用的部分是否足够 |
| Context Recall | 关键证据是否被覆盖 |
| Context Relevance | 检索内容是否跑题 |
| Context Correctness | 检索内容本身是否失真 |

如果是分类、拒答或结构化场景，再考虑：

| 基础指标族 | 更适合拆成什么细粒度方向 |
|---|---|
| Topic Adherence | 是否越过任务边界、是否路由错题型 |
| Refusal Quality | 该拒答时是否正确拒答、不该拒答时是否误拒 |
| Simple Criteria | 某个关键业务规则是否满足 |
| SQL Semantic Equivalence | SQL 结果语义是否等价 |

但要注意：

- 这些“规则 / 结构化”指标不应默认顶替模型主判
- 默认仍然先讨论模型评判是否能完成主评分
- 只有当用户明确要求硬规则，或模型评判确实无法稳定覆盖需求时，再把规则判定提升为主门禁或 fallback

## 如何和流程特色对齐

不要把“agent 类型”理解成固定指标菜单。

更推荐按下面这些特色去想：

| 流程特色 / 关键点 | 更值得优先看的 E2E 方向 |
|---|---|
| 最终回答本身是核心产物 | 关键结果是否成立、是否回答了用户真正问题 |
| 任务完成度比措辞更重要 | 目标完成度、关键约束满足度、关键结果成立 |
| 强依赖检索或外部证据 | 幻觉风险、证据支撑充分性、上下文一致性 |
| 风险、安全、拒答边界很重要 | 幻觉风险、边界遵守、拒答是否正确 |
| 输出是分类或结构化结果 | 关键字段正确性、结构约束满足度、边界是否正确 |

类型仍然可以作为辅助参考，但不应替代对流程特色的判断。

## 第一版推荐选型表

下面这张表用于回答“第一版到底先上哪几个指标”。

总原则：

- 第一版默认推荐 2 到 4 个核心指标就够了
- 优先推荐细粒度指标，不要默认先上多个泛化大指标
- 先覆盖“是否完成任务”和“是否违背证据 / 上下文 / 约束”这两条主线
- RAG、安全、拒答、结构化场景再补专项扩展

### 默认推荐：任务完成 + 证据/风险双主线

| 角色 | 推荐指标方向 | 说明 |
|---|---|---|
| 主指标 | 目标完成度 / 关键结果成立 | 看用户真正要的结果是否达成 |
| 主指标 | 幻觉风险 / 证据越界 | 看回答有没有超出可见证据乱说 |
| 主指标 | 上下文一致性 / 前后不矛盾 | 看回答是否和用户问题、上下文、工具证据冲突 |
| 主指标 | 关键约束满足度 | 看是否满足用户限制、角色边界、场景规则 |

### 如果回答本身是主要交付物

| 角色 | 推荐指标方向 | 说明 |
|---|---|---|
| 主指标 | 回答是否解决用户真正问题 | 比泛化 `Relevance` 更聚焦 |
| 主指标 | 关键事实是否错误 | 比泛化 `Correctness` 更容易落地 |
| 辅助指标 | 是否给出可执行下一步 | 适合替代过泛的 `Helpfulness` |
| 观察项 | 是否过度冗长 | 第一版通常只观察，不急着进总分 |

### RAG / 检索 / 外部证据场景

| 角色 | 推荐指标方向 | 说明 |
|---|---|---|
| 主指标 | 幻觉风险 / 证据越界 | 默认优先级很高 |
| 主指标 | 证据支撑充分性 | 看关键结论是否能回链到证据 |
| 主指标 | 上下文一致性 | 看回答是否和检索结果、自身上下文冲突 |
| 扩展指标 | 检索命中质量 / 检索吸收质量 | 只有检索是关键路径时再上 |

### 安全 / 拒答 / 边界场景

| 角色 | 推荐指标方向 | 说明 |
|---|---|---|
| 主指标 | 边界遵守 / 约束满足 | 比直接上泛化正确性更重要 |
| 主指标 | 幻觉风险 | 看是否凭空给出不该给的内容 |
| 扩展指标 | 拒答是否正确 | 只有确实存在拒答策略时再上 |
| 风险项 | Toxicity | 默认单独看，不和主分直接平均 |

### 分类 / 结构化产物场景

| 角色 | 推荐指标方向 | 说明 |
|---|---|---|
| 主指标 | 关键字段正确性 | 聚焦最重要字段，而不是泛化整体正确性 |
| 主指标 | 结构约束满足度 | 看输出结构、格式、规则是否符合要求 |
| 扩展指标 | 边界是否正确 | 适合分类、路由、拒答边界问题 |
| 专项项 | SQL Semantic Equivalence | 只有 SQL 场景才需要 |

## 推荐的复用流程

建议和用户一起走这四步：

1. 列出当前平台已有的 E2E 指标名
2. 给每个指标写一句“它到底在评什么”
3. 判断它是否适合当前 agent
4. 把适合的指标保留，不适合的删掉，缺少的再自定义补充

走完这四步后，不要直接进入计划。

还必须显式请用户回答：

- 接受哪些指标
- 删除哪些指标
- 新增哪些指标
- 哪些指标只观察，不进总分

在用户确认前，这里的推荐组合都只是候选集，不能视为定稿，也不能进入开发计划。

可以直接整理成这张表：

| 当前指标名 | 含义 | 当前 agent 是否适用 | 保留 / 删除 / 补充说明 |

## 指标进总分建议

下面这张表用于回答“哪些指标适合进总分，哪些更适合只做观察”。

| 指标方向 | 默认角色 | 是否建议进总分 | 建议权重 | 备注 |
|---|---|---|---|---|
| 目标完成度 / 关键结果成立 | 主指标 | 是 | 高 | 默认优先级很高 |
| 幻觉风险 / 证据越界 | 主指标或风险指标 | 视口径 | 高或单独看 | 如果进总分，先统一方向 |
| 上下文一致性 / 前后不矛盾 | 主指标 | 是 | 高 | 很适合作为默认核心项 |
| 关键约束满足度 | 主指标 | 是 | 高 | 任务执行型或有边界时尤其重要 |
| 关键事实是否错误 | 主指标 | 是 | 中高 | 适合替代过泛 `Correctness` |
| 是否给出可执行下一步 | 辅助指标 | 视情况 | 中 | 适合替代过泛 `Helpfulness` |
| 是否过度冗长 | 观察项 | 通常否 | 低 | 第一版通常不建议高权重 |
| 检索命中质量 | 扩展指标 | 是（RAG） | 中 | 检索是关键路径时再纳入 |
| 检索吸收质量 | 扩展指标 | 是（RAG） | 中高 | 适合 RAG 深度分析 |
| Toxicity | 风险指标 | 否，默认单独看 | 无 | 更适合作为安全门禁 |
| Answer Critic / Simple Criteria | 规则指标 | 视情况 | 中 | 作为补充或门禁，不默认替代模型主判 |
| SQL Semantic Equivalence | 专项主指标 | 是（专项） | 高 | SQL 场景专用 |

## 泛化大指标如何处理

下面这些指标仍然有参考价值，但不建议作为第一版默认主推：

| 泛化指标 | 建议角色 | 原因 |
|---|---|---|
| Correctness / Answer Correctness | 可选候选 | 太容易变成“整体回答好不好”的大分 |
| Relevance / Answer Relevance | 可选候选 | 语义常和其他主指标重叠 |
| Helpfulness | 可选候选 | 容易把很多不同问题混成一个感受分 |
| Faithfulness | 可选候选或 prompt 基座 | 很有价值，但最好拆成更具体的“幻觉风险 / 证据支撑”口径 |

## 默认推荐

如果用户没有特别强的业务约束，默认建议：

1. 先复用现有平台里已经稳定的合适分项
2. 第一版只推荐 2 到 4 个核心指标
3. 优先推荐细粒度指标，泛化大指标放到可选候选区
4. 保留各维度独立分数
5. 风险类指标默认单独展示，不直接和主分一起平均
6. 如确实需要总览，可额外给一个简单总览分，但不要让它掩盖分项差异

E2E 特有补充：

- 默认先问“最关键的成功条件”和“最危险的失败模式”是什么，再选指标
- `Hallucination`、上下文一致性、关键约束满足度这类细粒度方向，通常比泛化大指标更值得先讨论
- `Conciseness` 第一版通常不建议给高权重
- `Correctness` / `Relevance` / `Helpfulness` 这类泛化大指标可以保留，但默认排在细粒度指标之后
- `Answer Critic`、`Simple Criteria` 这类规则项默认不应先于模型主判启用；如要主用，先和用户确认理由与边界

## 需要和用户确认的问题

- 你当前平台页面里已经有哪些 E2E 指标？
- 这些指标名背后是不是你们团队已经有共识的定义？
- 这轮推荐的 E2E 指标里，你接受哪些、删除哪些、还要补哪些？
- 哪些指标只做观察项，不进入第一版总分？
- 你现在更需要“调试归因”，还是“汇报总分”？
- 第一版是想先用简单平均，还是暂时不聚合？
- 如果做加权平均，权重由谁决定、多久更新一次？

这些问题在用户明确答复前，不应进入开发计划。
