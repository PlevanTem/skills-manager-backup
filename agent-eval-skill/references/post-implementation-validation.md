# 实现后验证与反馈迭代

这份文档是给“代码已经写完一版，但评测体系还没有真正稳定下来”的阶段使用的。

重点不是证明“代码能跑”，而是帮助用户回答三件事：

1. 平台里到底有没有拿到要评的 trace
2. 当前 `trajectory` / `e2e` 分数到底合不合理
3. 如果不合理，应该把什么证据反馈给 agent，才能继续优化下一轮

## 一、先记住一个原则

评测代码写完，不等于评测体系已经完成。

第一版最常见的问题不是“完全跑不起来”，而是：

- trace 选错了
- payload 取错了
- 关键字段运行时其实没拿到
- judge 看到了信息，但信息不足以支撑这个分数
- judge `reason` 和分数对不上
- 分数能产出，但并不符合业务直觉

所以代码完成后，必须再做一轮“人工抽检 + 问题反馈 + 定向优化”。

## 二、首轮验证前先确认 4 件事

开始验证前，先确认：

1. 当前 trace 在平台官网或 trace 查看页面里能看到
2. 你知道第一版验证入口是什么
3. 你知道日志从哪里拿
4. 你知道结果最终落在哪里

最少要能回答：

- `当前验证入口：...`
- `当前结果落点：...`
- `当前日志位置：...`
- `当前查看 trace 的页面或方式：...`

如果这四件事有任一说不清，不要急着判断分数，先让 agent 把验证入口、日志入口和结果落点讲清楚。

## 三、首轮验证怎么做

建议第一轮不要全量跑，先选 3 到 5 条代表性 trace。

优先选这些类型：

- 正常完成任务的样本
- 过程较长、可能触发压缩的样本
- 带特殊标签的样本
- 明显失败或行为异常的样本

然后按下面顺序验证。

### 第一步：先看平台里有没有目标 trace

先去平台官网或 trace 查看页面确认：

- 这批 trace 是不是目标 agent 产生的
- trace 时间范围对不对
- trace 数量是否符合预期
- 你打算抽检的那几条 trace 是否真实存在

如果这里就找不到 trace，先不要继续看分数，优先反馈：

- 目标 trace 不存在
- trace 筛选条件可能有误
- 平台配置 / 过滤条件可能不对

### 第二步：逐条看 `trajectory` / `e2e` 分数

对每条抽检样本，至少看：

- `trajectory` 总体是否符合你对“过程质量”的直觉
- `e2e` 总体是否符合你对“最终结果质量”的直觉
- 特殊标签有没有被正确打上
- 风险类分数是否方向正确

不要只看高低，还要看“为什么给这个分”。

### 第三步：对照 judge reason 反推 payload 是否构建正确

看到某条样本后，重点问自己：

1. judge `reason` 里引用的证据，是否真的来自这条 trace
2. judge 说的优点 / 问题，是否能从 payload 中找到依据
3. judge 是否因为 payload 缺字段而误判
4. `trajectory` 是否被最终结果过度影响
5. `e2e` 是否真的拿到了应该评估的最终回答

如果当前设计里，trajectory 只允许通过 `runtime_context` 暴露 session 级收尾摘要，那么还要额外检查：

6. `trajectory reason` 是否把 `session_outcome_summary` 一类收尾信息看得过重
7. judge 是否在用“结果不完整 / 没成功收尾”去直接否定前面的工具选择、参数构造、路由或上下文利用

如果出现这种情况，默认先按 payload 设计偏差处理，而不是先怀疑 judge 模型本身。

如果 `reason` 看起来“像在讲另一条样本”，或者只是在泛泛而谈，通常要优先怀疑：

- payload 字段拿错
- payload 压缩过度
- trajectory 暴露给 judge 的 session 收尾信息仍然过强
- `case_labels` 或 `flags` 被直接喂进 judge，造成先入为主
- 标签边界不清
- rubric 口径不够具体

### 第四步：看运行时日志，确认关键字段有没有真的取到

对关键字段，不需要打印全文，但至少要看到：

- `拿到`
- `为空`
- `缺失`

建议重点确认：

- 最终回答字段
- tool transcript 或过程摘要
- prompt / routing / runtime context
- 特殊标签推导所需字段
- 压缩命中字段

如果理论上应该有的数据，日志里长期显示为空或缺失，就不要继续把问题归咎于 judge，先把重点放回字段可得性。

## 四、看到问题时，先判断大概是哪一层

### 更像是 trace / 数据层问题

常见信号：

- 平台里就没有目标 trace
- trace 时间范围、agent_name、筛选条件不对
- 关键 observation 缺失
- 最终回答本身就没有被记录

### 更像是 payload 层问题

常见信号：

- judge `reason` 提到的内容和真实样本不一致
- 过程证据缺失，但最终结果被看得过重
- `trajectory reason` 明显在用 session outcome 去倒推否定前面的过程判断
- judge 明显在复述系统标签，而不是根据原始证据做判断
- `trajectory` 和 `e2e` 看起来像用了同一套核心评判信息
- 压缩后丢掉了关键语义

### 更像是 rubric / prompt 层问题

常见信号：

- payload 看起来对，但 judge `reason` 很空泛
- 不同样本的 reason 模板味太重
- 高分 / 低分信号写得不清，导致 judge 口径飘

### 更像是标签层问题

常见信号：

- 明显应该打的标签没打上
- 不该打的标签被误触发
- 标签触发后把评分方向带偏了

### 更像是输出层问题

常见信号：

- 分数已经算出来，但平台没看到
- report 落点不对
- trace 和 score 没正确关联

## 五、推荐的反馈方式

不要只反馈一句“这个分不对”。

请尽量按下面模板把问题发给 agent。

## 六、问题反馈模板

```md
# 评测问题反馈

- trace_id:
- 样本类型: 正常样本 / 压缩命中样本 / 特殊标签样本 / 异常样本
- 评测类型: trajectory / e2e / rag / label / 输出链路
- 不合理的分数项:
- 人工预期:
- judge reason 是否和分数对得上: 对得上 / 对不上 / 不确定
- 我怀疑的问题层:
  - trace / 数据层
  - payload 层
  - rubric / prompt 层
  - label 层
  - 输出层
- 我看到的现象:
- 相关截图或日志片段:
- 我希望 agent 下一步优先检查:
```

如果一次发现多条问题样本，建议一条样本写一份，避免不同问题混在一起。

## 七、把什么证据带给 agent 最有用

至少带回这些信息中的 3 到 5 项：

- trace_id
- 样本截图
- judge `reason`
- 对应分数
- 关键字段 presence 日志
- 压缩命中日志
- 输出落点信息
- 你的人工判断理由

如果日志很多，不要整段全贴，优先贴和该问题直接相关的关键片段。

## 八、agent 收到反馈后应该怎么迭代

默认优先顺序建议是：

1. 先查 trace / 数据是否正确
2. 再查 payload 是否拿对、切对、压缩对
3. 再查标签边界是否误触发
4. 再调整 rubric / judge prompt
5. 最后才考虑调整聚合方式或大改架构

不要因为第一轮结果“不太对”就直接整套重写。

更合理的做法是：

- 先修最明显的问题层
- 只重跑最小必要样本集
- 再抽检 3 到 5 条样本
- 再决定是否进入下一轮优化

## 九、什么时候可以说“第一版稳定了”

至少满足：

- 平台里能稳定看到目标 trace
- 关键字段运行时大多能拿到
- 3 到 5 条代表性样本的 `trajectory` / `e2e` 结果基本符合人工直觉
- judge `reason` 和分数大体一致
- 已知问题已经被记录，并有下一轮优化方向

如果还只能说“能跑起来”，那就还在首轮验证阶段，不要过早说“评测体系已经完成”。
