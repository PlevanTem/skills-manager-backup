# Trajectory 多维度指标参考

trajectory 不一定只能是一个总分。

如果 agent 的过程质量本身很重要，尤其是：

- 会自主选工具
- 会构造复杂参数
- 会基于上下文决定排查方向
- 会受路由规则、场景约束、角色边界影响
- 会出现 transfer、reject、retry、resume

那么更推荐把 trajectory 拆成多个维度，而不是只保留一个 `trajectory_score`。

## 可以从哪些维度拆

结合常见多步 agent 的过程评测口径，可以先整理出下面这些候选维度：

| 维度 | 核心在评什么 |
|---|---|
| 证据驱动性 | 方向切换是否由新证据支撑，而不是拍脑袋换策略 |
| 上下文连贯性 | 前后步骤、用户目标、已知上下文之间是否自洽，有没有明显矛盾 |
| 工具选择与参数构造 | 是否选对动作，并把参数构造成可执行、贴合上下文的样子 |
| 路由与约束边界 | 是否遵守 prompt、routing、角色边界和场景限制 |
| 任务推进与收敛 | 是否围绕目标持续推进，并逐步收束 |
| 效率 | 是否存在明显冗余、兜圈、重复试错 |
| 异常恢复与策略调整 | 遇到失败、空结果、超时、拒绝后，是否采取了合理恢复路径 |
| 收尾与停止时机 | 是否在信息足够时及时停下，而不是该停不停或过早结束 |

这些维度不代表第一版都要上，更适合作为“候选池”。

## 默认核心包先收紧到 3 到 5 个

如果用户只是想把原来单个 `trajectory_score` 升级成多维度版本，第一版默认更推荐 3 到 5 个优先维度，而不是上来就铺满 7 个甚至更多：

- 证据驱动性
- 上下文连贯性
- 工具选择与参数构造
- 路由与约束边界
- 任务推进与收敛

这组更适合作为默认核心包，因为它们更直接回答了 trajectory 最常见的几个尖锐问题：

- 有没有根据证据走，而不是乱换方向
- 有没有前后矛盾、忽略上下文或忽略用户真正目标
- 有没有选对动作，并把参数构造到位
- 有没有越权、违背边界或误走路由
- 有没有真的在推进问题，而不是看起来很忙

`效率`、`异常恢复与策略调整`、`收尾与停止时机` 更适合作为扩展维度，只在高成本、长链路、失败恢复频繁的场景重点推荐。

## Trajectory 是否可以参考最终结果

一般建议：可以参考极弱的 session 级收尾信息，但不应让最终结果主导过程评分。

推荐原则：

- 默认不再给 trajectory 单独结果字段
- 如果确实要补充收尾信息，优先只放 `runtime_context.session_status`、`runtime_context.session_outcome_summary` 一类 session 级摘要
- 不默认直接暴露完整 `final_answer`
- 这些 session 级摘要主要用于判断是否收敛、是否正常结束、是否恢复成功
- 不要让 judge 因为最终结果好坏而倒推否定或美化前面的过程

可以参考结果摘要的维度：

| 维度 | 是否可参考 session 级收尾摘要 | 说明 |
|---|---|---|
| 任务推进与收敛 | 可以 | 需要看过程是否真的走向完成 |
| 收尾与停止时机 | 可以 | 需要看是否在有结果后及时停止 |
| 异常恢复与策略调整 | 可以 | 需要看恢复后是否至少达成基本收敛 |
| 交互处理质量 | 视情况 | 当最终是否完成会影响交互闭环时可参考 |

原则上不应被最终结果主导的维度：

| 维度 | 为什么不应主看结果 |
|---|---|
| 工具选择 | 应按当时可见信息判断是否选对动作 |
| 参数构造 | 应看参数本身是否贴合任务与上下文 |
| 路由与约束遵守 | 应看有没有越界、违背约束 |
| 上下文利用 | 应看是否正确使用已知上下文 |
| 逻辑连贯性 | 应看步骤之间是否自洽 |
| 效率 | 应看是否存在冗余和绕路 |
| 证据驱动性 | 应看方向变化是否由新证据支撑 |
| 风险判断与动作克制 | 应看动作前判断是否谨慎 |
| 转交决策质量 | 应看转交本身是否合理，而不是仅看子流程结果 |

如果某条 trajectory reason 明显在用“最终结果不完整”去否定前面的工具选择、参数构造或路由判断，通常说明 judge 已经发生了结果倒推偏差。

## 可选扩展维度

在默认核心包之外，还可以根据 agent 形态增加一些“扩展维度”。

这些维度不是默认必选，但在特定场景下非常有价值。

| 扩展维度 | 核心在评什么 | 更适合什么场景 |
|---|---|---|
| 证据驱动性 | 是否基于新证据调整方向，而不是无根据切换策略 | 调试、排障、诊断型 agent |
| 异常恢复与策略调整 | 遇到失败、空结果、超时、拒绝后，是否采取了合理恢复路径 | retry、fallback、resume 很多的 agent |
| 风险判断与动作克制 | 是否在高风险动作前做了恰当判断，没有过度冒进 | shell、写操作、敏感工具场景 |
| 转交决策质量 | 是否该转交、转交时机是否正确、转交前分析是否充分 | transfer / subagent 型 |
| 交互处理质量 | 面对用户拒绝、取消、未授权时，是否正确解释并给出下一步 | human-in-the-loop 型 |
| 收尾与停止时机 | 是否在信息足够时及时收束，而不是该停不停或过早结束 | 多轮探索、长链路任务 |

## 这些扩展维度如何理解

### 证据驱动性

它和“逻辑连贯性”相近，但不完全相同。

- 逻辑连贯性看的是“前后是否自洽”
- 证据驱动性看的是“方向变化是否由新证据支撑”

适合：

- 排障型 agent
- 调试 agent
- 会大量观察日志、状态、错误信息的 agent

### 异常恢复与策略调整

适合评估：

- tool 失败后是否换了合理路径
- 检索结果为空后是否调整 query
- 用户拒绝后是否给出替代方案
- resume 后是否从正确节点继续

这个维度和“任务推进与收敛”有关，但更聚焦在“失败之后怎么恢复”。

### 风险判断与动作克制

适合：

- 会执行命令
- 会改配置
- 会调用高风险工具
- 有明确安全等级或审批机制

这个维度看的是：

- agent 有没有在风险动作前做足判断
- 有没有为了追求效率而越过边界
- 有没有出现本应谨慎却过度冒进的行为

### 转交决策质量

这个维度在 transfer 型 agent 中很重要。

它关注的不是子流程内部做得多好，而是：

- 当前 agent 该不该转
- 转交是不是转得太早或太晚
- handoff 前的信息准备是否足够

### 交互处理质量

适合：

- 需要用户批准
- 存在授权失败
- 存在用户拒绝执行

这个维度看的是：

- agent 是否正确理解用户反馈
- 被拒绝后有没有合理 fallback
- 是否把“拒绝工具”误判成“用户放弃任务”

### 收尾与停止时机

适合：

- 多步探索容易越走越长的 agent
- 容易在“已经够了”和“还差一步”之间拿捏不准的场景

这个维度主要看：

- 什么时候该停
- 什么时候该继续
- 有没有“信息够了还在兜圈”
- 有没有“证据不够就急着结束”

## 各维度更适合什么场景

### 逻辑连贯性

适合：

- ReAct 型 agent
- 多步推理或多轮 tool use
- 容易出现“突然换方向”的场景

不一定重要：

- 几乎纯固定流程、每一步都由代码强约束的 agent

### 任务推进与收敛

适合：

- 要解决真实问题而不是单步回答的 agent
- 问题复杂、可能需要多次观察和缩小范围的场景

### 效率

适合：

- 工具调用有明显成本
- 冗余步骤会影响体验或费用

注意：

- 不要机械追求最短路径
- 复杂任务允许合理的探索步骤

### 上下文利用

适合：

- runtime_context 很关键
- 用户环境、代码信息、当前 tab、引用内容会强影响动作选择

### 路由与约束遵守

适合：

- 有明确 routing prompt
- 有角色边界、工具边界、场景限制
- 有业务 guardrail

### 工具选择

适合：

- ReAct 型
- 工具很多、容易选错
- 某些工具调用代价高或风险高

### 参数构造

适合：

- 参数质量强烈影响工具结果
- 参数需要融合上下文、历史消息或限制条件

## 扩展维度更适合什么场景

### 证据驱动性

适合：

- 调试 / 排障型 agent
- 多轮观察后动态调整方向

不一定重要：

- 固定流程型、几乎不做策略切换的 agent

### 异常恢复与策略调整

适合：

- tool 失败频繁
- 空结果、超时、拒绝较常见
- 有 retry / fallback / resume

### 风险判断与动作克制

适合：

- 命令执行型
- 配置修改型
- 需要审批或存在安全等级

### 转交决策质量

适合：

- transfer / subagent
- 多角色协作

### 交互处理质量

适合：

- human approval
- reject / cancel / unauthorized

### 收尾与停止时机

适合：

- 长链路排查
- 多轮探索
- 可能“该停不停”的 agent

## 第一版推荐选型

下面这些推荐组合是启发式参考，不是“只要分到某类 agent 就必须照抄”的固定映射。

更合理的用法是：

1. 先看当前 agent 的关键步骤和关键风险
2. 再从下面最接近的组合里挑维度
3. 最后根据 payload 可得性和用户目标删减

### 工具自由选择 / ReAct 倾向明显

| 角色 | 推荐维度 | 说明 |
|---|---|---|
| 主维度 | 工具选择与参数构造 | 默认建议合并先看，避免第一版维度太碎 |
| 主维度 | 证据驱动性 | 这是 ReAct 里很关键的过程质量信号 |
| 主维度 | 任务推进与收敛 | 看是否真的在解决问题 |
| 主维度 | 路由与约束边界 | 工具自由越高，越要看有没有越界 |
| 辅助维度 | 上下文连贯性 | 适合识别忽略上下文或前后矛盾 |
| 可选扩展 | 效率 | 高成本工具较多时再重点纳入 |
| 可选扩展 | 异常恢复与策略调整 | 如果失败与 fallback 很常见，建议加上 |

### 固定流程 / 步骤约束明显

| 角色 | 推荐维度 | 说明 |
|---|---|---|
| 主维度 | 任务推进与收敛 | 看流程是否真的完成任务 |
| 主维度 | 路由与约束边界 | 固定流程常更依赖边界是否被遵守 |
| 主维度 | 上下文连贯性 | 看前后节点是否衔接正确、有没有自相矛盾 |
| 辅助维度 | 工具选择与参数构造 | 只有参数质量会明显影响结果时再上主维度 |
| 观察项 | 效率 | 只在流程分支很多时才值得重点看 |
| 可选扩展 | 收尾与停止时机 | 如果流程结束条件复杂，值得增加 |

### 检索 / 证据驱动明显

| 角色 | 推荐维度 | 说明 |
|---|---|---|
| 主维度 | 证据驱动性 | 看是否依据检索结果合理调整方向 |
| 主维度 | 上下文连贯性 | 看回答前的过程是否和检索证据一致 |
| 主维度 | 工具选择与参数构造 | 看是否在该检索时检索、query 是否合理 |
| 辅助维度 | 路由与约束边界 | 特别适合有知识回答限制的场景 |
| 可选扩展 | 任务推进与收敛 | 如果流程很长，建议补上 |

### Transfer / Subagent 明显

| 角色 | 推荐维度 | 说明 |
|---|---|---|
| 主维度 | 任务推进与收敛 | 看 transfer 是否推动了解题 |
| 主维度 | 路由与约束边界 | 看是否在正确边界内转交 |
| 主维度 | 工具选择与参数构造 | handoff payload 是否充分、转交动作是否合理 |
| 辅助维度 | 上下文连贯性 | 看转交前分析是否合理、是否与已有线索冲突 |
| 可选扩展 | 转交决策质量 | 如果 transfer 是核心能力，建议单独拆维度 |

### Human-in-the-loop 明显

| 角色 | 推荐维度 | 说明 |
|---|---|---|
| 主维度 | 工具选择与参数构造 | 被拒绝前提议本身是否合理、参数是否贴合任务 |
| 主维度 | 路由与约束边界 | 是否正确处理批准、拒绝、授权边界 |
| 主维度 | 上下文连贯性 | 是否正确理解用户反馈和当前执行状态 |
| 辅助维度 | 任务推进与收敛 | 拒绝后是否还有合理 fallback |
| 可选扩展 | 交互处理质量 | 如果拒绝、取消、授权是核心场景，建议单独拆 |

### 调试 / 排障目标明显

| 角色 | 推荐维度 | 说明 |
|---|---|---|
| 主维度 | 任务推进与收敛 | 看是否真正缩小问题范围 |
| 主维度 | 证据驱动性 | 看是否根据新日志、新状态调整方向 |
| 主维度 | 上下文连贯性 | 看是否正确吸收环境和历史上下文，避免前后冲突 |
| 辅助维度 | 工具选择与参数构造 | 看观察动作与查询参数是否合理 |
| 辅助维度 | 异常恢复与策略调整 | 看失败后是否及时换路径 |

## 推荐维度确认门

上面的 trajectory 维度和推荐组合都只是候选集，不是默认定稿。

在继续做 payload、spec 或开发计划前，必须先让用户明确回答：

- 接受哪些主维度
- 删除哪些维度
- 要新增哪些维度
- 哪些维度只做观察项，不进第一版总分

如果用户还没有确认，这里只能停留在“推荐维度集合”，不能进入后续计划。

## 不建议一上来就拆太多维度

虽然 trajectory 可以拆很多维度，但第一版默认更建议先控制在 3 到 5 个主维度。

原因：

- judge prompt 会变重
- 维度之间更容易重叠
- Langfuse score schema 更复杂
- 用户更难理解每个维度的边界

默认建议：

1. 先从默认核心包里挑 3 到 5 个最相关的
2. 只有在业务确实强依赖时，再加入扩展维度
3. 扩展维度优先先做 breakdown，再决定要不要进总分
4. 如果超过 5 个主维度，要明确向用户解释为什么不能继续收紧

## 单总分 vs 分项分数

### 只保留一个 trajectory 总分

适合：

- 第一版很轻量
- 团队只想快速看趋势
- 当前没有精力维护分项 schema

缺点：

- 很难定位到底是工具选错、参数错，还是上下文没用好

### 保留一个总分 + 多个分项 breakdown

适合：

- 大多数实际项目第一版升级
- 既想看总览，又想保留归因能力

推荐做法：

- Langfuse 上保留一个 `trajectory_score`
- 同时在 metadata 中存 `trajectory_score_breakdown`

### 每个维度单独作为 score

适合：

- 团队已经明确要长期维护 trajectory 体系
- 需要按维度筛选和看趋势

成本：

- score schema 更多
- 聚合和版本管理更复杂

## 维度进总分建议

| 维度 | 是否建议进 trajectory 总分 | 建议权重 | 备注 |
|---|---|---|---|
| 逻辑连贯性 | 是 | 中 | 多步 agent 很重要 |
| 任务推进与收敛 | 是 | 高 | 最能体现是否在解决问题 |
| 效率 | 视情况 | 低 | 第一版不建议给太高权重 |
| 上下文利用 | 是 | 中高 | 有 runtime_context 时尤其重要 |
| 路由与约束遵守 | 是 | 高 | 有 guardrail 时应提高权重 |
| 工具选择 | 是 | 高 | ReAct / tool-heavy 场景核心项 |
| 参数构造 | 是 | 高 | 参数质量直接影响执行质量 |
| 证据驱动性 | 视情况 | 中高 | 调试 / 排障型很有价值 |
| 异常恢复与策略调整 | 视情况 | 中 | 失败恢复很多时值得提高权重 |
| 风险判断与动作克制 | 视情况 | 高 | 高风险动作场景下建议重点纳入 |
| 转交决策质量 | 视情况 | 高 | transfer 是核心能力时建议纳入 |
| 交互处理质量 | 视情况 | 中高 | 人工确认型场景很重要 |
| 收尾与停止时机 | 视情况 | 中 | 长链路任务中价值较高 |

## 默认聚合建议

trajectory 的聚合主规则请统一参考：

- [输出策略](output-strategies.md)

这里保留 trajectory 场景自己的默认补充：

1. 第一版至少保留分项 breakdown
2. 可以保留一个 `trajectory_score` 做总览
3. `效率` 默认低权重，避免机械压制复杂任务
4. 扩展维度优先先做 breakdown，再决定要不要进总分

## 推荐默认权重思路

不是固定比例，只是 trajectory 维度的默认偏好：

- 高权重候选：任务推进与收敛、工具选择、参数构造、路由与约束遵守
- 中权重候选：逻辑连贯性、上下文利用
- 低权重候选：效率

如果加入扩展维度，可以按下面这个思路调：

- 高权重扩展候选：风险判断与动作克制、转交决策质量
- 中高权重扩展候选：证据驱动性、交互处理质量
- 中权重扩展候选：异常恢复与策略调整、收尾与停止时机

如果 agent 基本不用工具，就把“工具选择 / 参数构造”的权重降下去。

## 需要和用户确认的问题

- trajectory 是只保留一个总分，还是拆成多维度？
- 推荐的主维度、辅助维度、观察项，你接受哪些、要删哪些、要补哪些？
- 分项是只放 metadata，还是单独写回 Langfuse score？
- 哪些维度最影响业务结果，应该给高权重？
- 效率是重要体验指标，还是只做辅助观察？
- transfer、reject、resume 这些特殊行为是否需要单独维度？

这些问题在用户明确答复前，不应进入开发计划。
