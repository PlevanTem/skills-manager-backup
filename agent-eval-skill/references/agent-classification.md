# Agent 特色识别与参考分类

在定义评分规则前，先识别 agent 的流程特色、关键风险和关键产物，再把“类型”当成辅助参考。

不要把分类当成硬入口，也不要因为 agent 被归到某一类，就机械套一组固定指标。

## 先看什么，不要先急着分类型

先回答这些问题：

- 工具选择是模型自由决定，还是代码固定流程决定？
- 哪些中间步骤真的值得单独评分？
- 有没有 retrieval、rerank、外部知识注入？
- 有没有 transfer、subagent、handoff？
- 有没有 human approval、reject、resume、authorize？
- 最终产物是自然语言、结构化结果、动作执行结果，还是混合？
- 最关键的错误模式是什么：幻觉、误路由、错误调用、漏执行、恢复失败，还是别的？

这些问题比“先分到哪一类”更重要，因为它们直接影响你要选哪些指标、哪些 payload block、哪些标签边界。

更进一步说：

- 不要先问“这轮要不要直接上 `Correctness` / `Helpfulness` / `Relevance`”
- 更应该先问“当前 agent 最重要的成功条件、失败模式、边界风险分别是什么”
- 然后再从基础指标族里裁出当前 agent 的细粒度指标名

## 常见参考类型

### ReAct / 自主选工具型

代码特征通常是：

- 模型自由决定调哪些工具
- 多个工具同时暴露给 LLM
- tool 选择和参数构造高度依赖模型决策
- 代码不强制规定每一步顺序

常见评测重点：

- trajectory 合理性
- tool 选择质量
- 参数构造质量
- 重试、绕路、恢复行为
- 最终回答质量

### 固定流程 / 步骤驱动型

代码特征通常是：

- 明确的 graph、pipeline 或 workflow
- 步骤顺序由代码强制定义
- 每个节点职责较窄
- 中间结果本身就有明确预期

常见评测重点：

- 每一步输入输出是否符合预期
- 步骤衔接是否正确
- 哪一步最容易失真
- 最终回答是否建立在正确的中间步骤上

### RAG 型

代码特征通常是：

- 有检索、召回、rerank 工具
- 有检索专用 prompt
- 会把检索结果拼进上下文
- 有引用、证据、知识约束

常见评测重点：

- retrieval relevance
- retrieval usage quality
- groundedness
- 什么时候该检索、什么时候不该检索

### Transfer / Subagent 型

代码特征通常是：

- 有 transfer 工具
- 会路由到子 agent
- 子流程和当前 agent 有明显边界
- 转交前会组装 handoff payload

常见评测重点：

- 是否应该转交
- 转交时机是否合理
- 转交 payload 是否完整
- 子流程是黑盒评估还是继续展开评估

### Human-in-the-loop 型

代码特征通常是：

- interrupt
- approval prompt
- reject / cancel / authorize 分支
- resume map、checkpoint、恢复执行逻辑

常见评测重点：

- 工具提议本身是否合理
- 被拒绝后的 fallback 是否合理
- 是否正确理解了用户批准状态
- 标签边界是否清楚

## 分类输出方式

不要强迫只选一个类型，一个 agent 往往是组合型的。

建议输出格式：

`Primary: ReAct + human-in-the-loop`

`Secondary: RAG`

更推荐再补一段“流程特色摘要”，例如：

`Key traits: tool-heavy, retrieval-dependent, approval-gated, final answer + action mixed`

## 类型与指标的关系

类型和指标之间只应该是“启发式参考”，不是固定映射。

更合理的顺序是：

1. 先识别关键步骤、关键风险、关键产物
2. 再判断哪些 trajectory / E2E / 风险 / 规则指标族值得参考
3. 基于这些指标族，定制出更贴近当前 agent 的细粒度指标名
4. 最后才参考常见类型，检查自己有没有漏掉重要维度

也就是说：

- `RAG 型` 不等于必须上全部 RAG 指标
- `Human-in-the-loop 型` 不等于一定要把交互处理拆成独立维度
- `固定流程型` 也不等于一定要做逐步骤评分
- 平台里现成有 `Correctness`、`Faithfulness`、`Goal Accuracy`，也不等于第一版就应该直接照搬这些名字

## 如何从基础指标族定制出当前 agent 的指标

推荐顺序：

1. 先写出当前 agent 最关键的 2 到 4 个成功条件
2. 再写出最危险的 2 到 4 个失败模式
3. 看哪些是过程问题，哪些是结果问题，哪些是风险或边界问题
4. 最后再回头找最接近的基础指标族和 prompt 参考

例如：

- 不要只写 `Correctness`
- 更可以写成 `关键事实是否错误`、`关键结果是否成立`
- 不要只写 `Faithfulness`
- 更可以写成 `是否出现证据越界`、`是否和检索证据矛盾`
- 不要只写 `Helpfulness`
- 更可以写成 `是否给出可执行下一步`

这样做的目的不是完全抛弃通用指标，而是避免 judge 最后只得到几个语义很宽的大词。

是否纳入，最终还是取决于：

- 当前 agent 最关键的成败点
- 现有 trace / payload 能否支撑评判
- 用户更关心调试归因、验收结果，还是平台内长期看板

## 需要和用户确认的问题

- 模型是否真的自由选工具，还是代码已经限制了步骤顺序？
- 中间状态本身值不值得单独评分？
- 检索是必须动作、可选动作，还是只是偶发能力？
- transfer 是否意味着当前评测范围结束？
- 用户拒绝执行是标签、扣分项，还是独立分支？
- 哪些流程特色只是背景信息，哪些真的决定了指标选型？
