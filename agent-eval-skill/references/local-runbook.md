# 本地运行指引

这份文档回答一个很实际的问题：

“如果用户已经确认了评测方案，下一步在本地最小可运行链路到底怎么搭？”

## 目标

让用户至少能在本地跑通一条最小评测链路：

`trace 获取 -> payload 生成 -> judge 执行 -> score 输出`

不要求第一版就接全量生产流量，但必须能对代表性样本跑通。

## 开始前先确认项目落位

在讨论链路之前，先确认三件事：

| 检查项 | 需要确认什么 |
|---|---|
| 评测项目位置 | 当前评测工作落在哪个仓库或目录 |
| 配置位置 | 环境变量、judge 配置、trace 接入配置、CI 配置分别在哪里 |
| 代码落点 | 新评测代码准备放进现有项目，还是新建 `eval/` / `evaluation/` 目录 |

如果这些还没确认，就先继续 discovery，不要直接进入 runner 设计。

## 无现成评测项目时的最小初始化

如果用户没有现成评测项目，不要直接默认目录结构或技术栈。

先确认：

| 检查项 | 需要确认什么 |
|---|---|
| 语言 / 运行时 | 例如 `TypeScript`、`Python`、`Go` |
| 框架 / 最小实现方式 | 例如 `trpc`、CLI、脚本、服务化 runner |
| 同仓 / 异仓 | 跟 agent 仓库同仓，还是独立评测仓库 |
| 配置承载方式 | env、配置文件、项目配置中心、密钥管理 |
| 最小 runner 入口 | 第一版从哪里启动评测链路 |

如果这些还没确认，不要直接开始设计实现目录和依赖。

## 先盘点原有评测项目里能复用什么

如果用户已经有评测项目，不要默认新建整套链路。

先检查是否已经有这些可复用部分：

- trace reader / data fetcher
- sample selector
- payload builder
- label / flag 推导
- judge prompt
- judge client / executor
- score writer
- report runner
- fixture / golden trace 结构
- config schema

建议整理一张表：

| 组件 / 契约 | 位置 | 当前作用 | 是否可复用 | 适配方式 |
|---|---|---|---|---|
|  |  |  |  |  |

## 先决定本地跑哪条链路

### 链路 A：平台 DB / API 驱动

适合：

- 已经有可用的 tracing / 评测平台项目
- 能拿到 trace、observations、prompt 或 score 接口

最小流程：

1. 从平台 DB 或 API 读取目标 traces
2. 按选定评测单元切成评测样本
3. 生成 trajectory payload / E2E payload
4. 调用 judge
5. 写回平台 score，或先写到本地结果文件

如果当前 DB 配置缺失，先不要直接放弃：

1. 先问用户是否能补到数据库配置
2. 如果短期补不到，再讨论是否改走 SDK / API
3. 如果 SDK / API 也不可行，再退到导出文件方案

### 链路 B：导出 trace 文件驱动

适合：

- 没有 DB
- 只有导出 JSON / CSV / trace 文件

最小流程：

1. 读取导出 trace 文件
2. 归一化成统一中间结构
3. 生成 payload
4. 调用 judge
5. 输出本地 JSON / markdown / CSV 结果

### 链路 C：仅设计，不立刻运行

适合：

- 还没有足够 trace
- 先想把 spec、labels、payload 定下来

最小产物：

1. spec
2. payload 模板
3. label 表
4. observability backlog
5. 本地最小运行计划

## 执行方式选择

在真正开始验证前，先和用户确认用哪种执行方式：

| 方式 | 适合什么情况 | 要额外确认什么 |
|---|---|---|
| 本地直接运行 | 本地依赖和配置都能拿到 | 本地命令、环境变量、日志落点 |
| 手动打包后运行 | 本地环境不完整，但可打包可传递 | 包内容、配置注入方式、结果回传方式 |
| 发布到测试环境 | 需要依赖在线服务或隔离网络 | 发布流程、日志获取方式、回滚方式 |
| 使用 `dtools` 或等价工具 | 用户已有工具链可把任务投到测试环境 | 入口命令、环境差异、日志复制方式 |

不要默认“本地直接跑”一定可行；如果环境隔离明显，提前把日志和结果如何回收问清楚。

## 接口还是内部 runner

在实现前，必须明确这套评测是：

1. 只提供内部 runner / 脚本
2. 对外暴露接口
3. 两者都要

如果要暴露接口，测试前至少要先告诉用户：

- 当前接口是单条 trace 评测，还是时间范围 / 条件批量评测
- 如果是批量接口，每条 trace 是否并行执行
- 并行量上限是多少
- 触发批量时的筛选条件是什么
- 测试接口是什么
- 请求参数长什么样
- 返回结果里哪些字段最关键
- 测试环境怎么调用

如果第一版只保留内部 runner，也要明确入口命令和触发方式，避免用户以为已经具备可对外调用能力。

但要注意：并行确认不能只在“接口”场景里问。

只要存在批量评测，不管入口是：

- 对外接口
- 内部 runner
- 离线脚本
- 定时任务

都必须确认：

- 并行单位是 trace、sample，还是 judge request
- 是否允许并行
- 并行量上限是多少
- 是否要限流
- 单条失败时是重试单条、中止整批，还是跳过继续

建议直接用这种对用户的回报方式：

- `当前测试接口：...`
- `调用方式：...`
- `关键输入：...`
- `关键输出：...`

如果没有接口，就主动告诉用户：

- `当前没有对外测试接口`
- `当前可用入口：...`
- `触发方式：...`

## 本地运行前必须确认的 6 件事

| 检查项 | 必须回答的问题 |
|---|---|
| 评测单元 | 是按 session、turn、trace，还是按任务实例评？ |
| 数据入口 | trace 从 DB、API 还是文件来？ |
| ground truth 策略 | 有标准答案、参考轨迹，还是只能用 judge / rubric？ |
| judge 位置 | judge 在当前平台、独立服务、还是本地脚本？ |
| score 去向 | 写回当前平台、写数据库、还是只生成本地报告？ |
| 验证方式 | 本地怎么验、CI 怎么验？ |

## 配置获取失败时怎么继续

### 数据库配置不可用

优先顺序：

1. 询问用户后续是否能获取到 DB 配置
2. 如果能，先按 DB 路线做设计，但标记为待补配置
3. 如果不能，转为 SDK / API 路线

如果问题不是“配置缺失”，而是“agent 本地所在环境无法正确执行数据库查询”，也不能直接由 agent 自己拍板。

必须先让用户显式选择：

1. `我愿意手动改配置并去数据库验证关键字段`
2. `我现在不想查库，先接受风险继续搭建体系`
3. `我更希望改走 SDK / API / 导出文件`

如果用户选择 `1`，agent 至少要提供这类指导：

- 需要在哪个环境执行查询
- 需要改哪些配置值
- 重点查哪些 payload / label 关键字段
- 需要带回哪些截图、结果或日志

如果用户选择 `2`，agent 必须明确告诉用户：

- 当前是在“带风险继续”
- 哪些字段只是理论上可取，还没被真实验证
- 一旦后续评分异常、judge `reason` 信息缺失或标签异常，就要优先回头做字段验证

如果用户选择 `3`，再进入 SDK / API / 导出文件路径的 reduced-scope 设计。

### SDK / API 也不可用

这时再退到：

1. 导出 trace 文件驱动
2. 或仅设计阶段，先补 observability backlog

## 模型配置确认

在本地可运行链路落地前，必须问清楚：

| 配置项 | 必须确认什么 |
|---|---|
| 默认 judge 模型 | 当前项目到底用哪个模型作为默认 evaluator |
| 大上下文兜底模型 | 是否配置一个更大上下文模型处理长 payload |
| 触发切换条件 | 什么时候从默认模型切到兜底模型 |
| 超时阈值 | 多久没有返回算超时，例如多少分钟 |
| 超时后的动作 | 是重试、切兜底模型、降并发，还是直接失败 |
| 无兜底模型时怎么办 | 用户是接受跳过、加强压缩，还是别的策略 |

如果默认模型或兜底模型不清楚，不要由 agent 自己假设。

这些问题不是“实现时看情况再说”，而是批量运行前必须确认的前置条件。

## 日志设计与验证

评测链路不是“能跑起来”就够了，日志至少要覆盖设计里的关键点。

推荐最小日志覆盖面：

| 阶段 | 至少记录什么 |
|---|---|
| sample 选择 | trace / sample 是怎么筛出来的 |
| payload 生成 | 取了哪些 block，哪些字段缺失，哪些关键字段拿到 / 为空 / 缺失 |
| 压缩命中 | 哪些字段被 trim / 摘要 / 降级 |
| judge 请求 | 使用了哪个模型、哪个 prompt / rubric 版本 |
| judge 响应解析 | 是否解析成功、失败原因是什么 |
| score 输出 | 输出到了哪里、主键或 trace 标识是什么 |

日志至少要能帮助用户回答：

- 这条样本为什么被评
- judge 实际看到了什么级别的信息
- 关键 payload 字段到底有没有在运行时真实取到
- 为什么某些字段被压缩或省略
- 分数最终落到了哪里

如果当前无法查库，更建议先准备：

- 单条 trace 的 payload inspect / preview 入口
- 关键字段 presence logging
- 关键 flags / labels 的证据链日志

这样即使先延后查库，也能在评分异常时更快定位是否是字段拿错。

## 日志采集与复盘

先确认日志怎么拿：

| 场景 | 推荐做法 |
|---|---|
| 本地直接运行 | 直接看本地 stdout / 文件日志 |
| 测试环境运行 | 提前告诉用户需要复制哪些关键日志片段 |
| 环境隔离明显 | 先约定最小日志格式，避免拿回来的日志不足以排障 |

如果用户无法把完整日志带回，至少要求其复制：

1. sample 选择日志
2. payload 生成与压缩命中日志
3. 关键字段 presence 日志（拿到 / 为空 / 缺失 + 长度或条数）
4. judge 请求 / 响应解析日志
5. 最终 score / report 输出日志

跑通后，不要只看“有没有结果文件”。

至少抽样分析 3 到 5 条评测结果，检查：

- 标签是否符合预期
- payload 是否包含真正支持判断的字段
- 那些理论上可取的关键字段，运行时是否真的拿到了
- 压缩后是否还保留关键语义
- judge 的 reason 是否和分数一致
- 是否需要回头优化 payload / rubric / labels

## 平台关键配置确认

如果链路依赖 Langfuse 或等价平台，至少要确认：

| 配置项 | 为什么必须确认 |
|---|---|
| project / space 对应关系 | 不清楚就无法锁定 trace 范围 |
| base URL（如适用） | 影响读取与回写目标 |
| 鉴权方式 | 决定本地如何接入 |
| 密钥是否已配置 | 没有密钥就不能默认假设可读可写 |
| `agent_name` 或等价筛选字段 | 决定 sample / trace 如何过滤 |
| trace 过滤维度 | 决定回放和回写是否打到正确对象 |

在这些信息未确认前，不能把“平台路径已可用”当成事实。

## 本地最小目录建议

不是强制结构，但建议至少把下面几类内容分开：

```text
eval/
  fixtures/
  payloads/
  judges/
  reports/
  README.md
```

对应关系：

- `fixtures/`：代表性 trace、golden case、ground truth
- `payloads/`：用于调试 payload 生成结果
- `judges/`：judge prompt 或调用封装
- `reports/`：本地输出结果

如果用户已经有现成评测仓库，优先落在现有结构里；只有当现有项目没有合适承载位置时，才建议新建独立 `eval/` 目录。

## 临时硬编码的边界

如果用户暂时无法提供配置，可以建议短期硬编码，但必须同时满足：

1. 用户明确同意
2. 明确标为 `TEMP`
3. 写清楚后续替换条件
4. 在 spec 和 checklist 里保留痕迹

不要把临时硬编码写成默认推荐路径。

## 推荐的本地实现顺序

### 第一步：先跑通 fixture -> payload

不要一上来就连平台回写。

先用少量固定样本确认：

- payload 字段是否齐
- labels 是否对
- 压缩策略是否符合预期

### 第二步：再跑通 payload -> judge 输出

先确保 judge 输出能稳定解析：

- JSON 字段齐全
- score 方向一致
- parse 失败能降级

### 第三步：最后接 score 输出

只有前两步稳定后，再接：

- 平台 score 回写
- 或本地报告输出

### 第四步：抽样复盘结果

用少量代表性样本做人工复盘，而不是只看汇总均分。

建议至少覆盖：

- 正常成功样本
- 有 fallback 或压缩命中的样本
- 有特殊标签的样本
- 一条明显失败或边界样本

## 本地最小验证建议

### payload 层

至少验证：

- 评测单元切分正确
- 缺字段 fallback 正确
- labels 推导正确
- 压缩策略正确

### judge 层

至少验证：

- judge 输出字段可解析
- score 范围合法
- summary / reason 不为空或有合理 fallback

### score 输出层

至少验证：

- score 名和 metadata 正确
- 重复运行时不会造成不可控重复
- 本地结果文件结构稳定

### 日志层

至少验证：

- 日志能覆盖 sample 选择、payload 生成、压缩命中、judge 执行、score 输出
- 日志能看出关键 payload 字段是“拿到 / 为空 / 缺失”
- 日志字段足以让用户复盘单条样本
- 环境隔离时，日志可以被用户手动复制回来做排障

## 本地运行时的三种降级策略

| 问题 | 降级方式 |
|---|---|
| 平台 DB 暂时不可用 | 改用 API 或导出 trace 文件 |
| judge 服务不稳定 | 先只产出 payload 和本地中间结果 |
| score 暂时不回写 | 先落本地 JSON / markdown 报告 |

## 报错修理与再验证

如果运行时报错，不要一次性大改全部环节。

推荐排查顺序：

1. 配置和数据入口是否正确
2. sample 切分是否正确
3. payload 构造和压缩是否正确
4. judge 请求参数和响应解析是否正确
5. score 输出或报告落盘是否正确

修理后最少要重跑：

1. 出问题的最小样本
2. 一条正常样本
3. 一条边界或带标签样本

只有这三类都复核过，才能说修复没有明显破坏主链路。

## 第一版完成标准

第一版不要求“全部自动化”，但至少应满足：

- 能对一批固定样本跑出 payload
- 能得到可解析的 judge 输出
- 能把结果落到平台或本地文件中的一个稳定出口
- 能重复运行并得到结构一致的结果
