# 可评测性检查

在讨论指标和 evaluator 之前，先判断用户当前到底有没有足够的数据基础。

这份文档的作用是给 discovery 阶段提供中间结论，不是直接给 implementation plan 开绿灯。

## 目标

判断当前的代码访问条件和 trace 条件，是否足以支持：

- 完整评测设计
- 缩减版评测设计
- 或者只能先做可观测性补齐建议

同时确认几个经常被忽略的前提：

- 评测项目本身在哪个仓库或目录
- 配置放在哪里
- 新评测代码准备落在哪里
- 当前到底能从哪里获取 trace 数据
- 是否已经有现成评测项目
- 如果没有，准备使用什么技术栈做第一版

## 项目落位检查

在判断数据是否足够前，先确认：

| 问题 | 为什么要先问 |
|---|---|
| 评测项目在哪个仓库 / 目录？ | 不知道项目位置，就不知道该读什么配置、把代码放哪 |
| 相关配置在哪？ | 包括环境变量、judge 配置、trace 接入配置、CI 配置 |
| 新评测代码准备放哪？ | 会影响后续如何组织 runner、payload builder、fixtures |

如果这些信息都没问清楚，就还处在 discovery 前半段，不能进入计划。

## 数据源优先级

1. **Langfuse DB**
2. **Langfuse SDK 或 API**
3. **导出 trace 文件**
4. **只有代码，没有 trace**

这四种情况不能一视同仁，越往后，可恢复的评测信息越少。

## 数据获取路径检查

在数据源之外，还要继续问：

- 数据库配置当前是否可用？
- 如果数据库配置拿不到，用户是否能补到？
- 如果补不到，是否能改走 SDK / API？
- 如果连 SDK / API 也不可用，是否只能退到导出 trace 文件？
- 如果依赖 Langfuse，project / space 对应关系是否清楚？
- 读 trace 和写 score 各自依赖哪些配置？
- `agent_name` 或等价筛选字段到底是什么，配置在哪里？
- 鉴权方式与密钥当前是否已配置好？

推荐判断顺序：

1. 先看 DB 能不能直接拿
2. 拿不到再问能不能补配置
3. 配置补不到再问能不能走 SDK / API
4. 最后才退到导出文件或纯指导模式

但要注意：如果不是“理论上 DB 可用”，而是“agent 本地执行不了数据库查询”，不能由 agent 代替用户直接决定后续路径。

必须显式询问用户在下面三种方案里选哪一种：

1. `手动改配置并查库验证关键字段`
2. `先接受风险延后验证，再继续搭建体系`
3. `改走 SDK / API / 导出文件，做 reduced-scope`

如果用户选择 `1`，至少要继续明确：

- 需要用户在哪个环境执行
- 需要用户改哪些配置值
- 需要用户验证哪些关键字段
- 需要用户把什么结果或截图带回

如果用户选择 `2`，必须明确写成：

- 当前是“带风险继续”
- 哪些关键字段还没被真实证明
- 什么时候必须回头做字段验证

不能把“用户嫌麻烦”自动翻译成“默认继续”。

## 无现成评测项目时怎么办

如果用户没有现成评测项目，不要直接进入评测设计。

先完成最小初始化选型：

| 问题 | 为什么要先问 |
|---|---|
| 目标语言 / 运行时是什么？ | 决定后续 runner、配置和依赖管理方式 |
| 框架或最小实现方式是什么？ | 例如 `trpc`、CLI runner、定时任务等 |
| 同仓还是异仓？ | 影响代码组织和配置复用 |
| 最小 runner 入口是什么？ | 决定第一版如何跑通 trace -> judge -> score |
| 配置承载方式是什么？ | env、配置文件、项目配置中心都不同 |

如果这些问题还没答清，就还不能进入指标和 payload 设计。

## 最低数据要求

优先确认用户是否能提供下列信息中的大部分：

| 字段 | 作用 |
|---|---|
| Trace ID / Run ID | 用于回链真实运行 |
| 用户输入 | trajectory 和 E2E 的基础 |
| 最终回答或最终结果 | E2E 评测所需 |
| Tool call 和 tool result | 过程评测和故障归因所需 |
| Prompt 名或 prompt 文本 | 当 prompt 对行为约束重要时需要 |
| Runtime metadata | 当环境、代码位置、上下文会影响评判时需要 |
| 错误 / 中断 / 取消信号 | 特殊标签边界所需 |
| 时间顺序信息 | 重建多步轨迹所需 |

## 代码扫描时必须关注的点

在 agent 代码里重点看：

- trace 从哪里创建
- trace 名称如何约定
- prompt 如何加载和命名
- metadata 在哪里挂到 trace 上
- tool call 和 tool result 如何序列化
- 用户拒绝、取消、未授权信号如何表达
- transfer 或 subagent 如何标记
- 最终输出从哪里流出

如果这些信息在代码里有，但 trace 里没有，就要明确记为“可观测性缺口”。

## Ready 结论分类

### 可做完整平台路径设计

适用条件：

- 有本地代码或足够完整的上传代码
- 有 Langfuse DB 或足够细的 observation 数据
- prompt、tool trace、metadata、final output 基本可恢复

建议产出：

- trajectory payload
- E2E payload
- label taxonomy
- 平台内 score 输出方案

### 可做缩减版设计

适用条件：

- 有代码 + 部分 trace
- 只有 SDK / API，没有 DB
- 导出 JSON 里缺 prompt context 或部分 metadata

建议产出：

- best-effort payload
- 缺失字段清单
- 下次需要补哪些 trace 字段的建议

### 暂不适合评分，但适合先做指导

适用条件：

- 基本只有 agent 代码
- trace 很少或不可用
- 连稳定的 final answer 信号都拿不到

建议产出：

- 可观测性缺口报告
- 建议补充的 trace / metadata 方案
- payload 愿望清单
- 标签草案

## 缺字段时怎么继续

缺字段不等于停工。优先找平替：

| 缺失字段 | 临时替代 | 代价 |
|---|---|---|
| Prompt 文本 | prompt 名、嵌入式默认 prompt、代码中推断的约束 | judge 精度下降 |
| Runtime metadata | 从代码或用户说明恢复部分环境信息 | groundedness 判断变弱 |
| 细粒度 tool result | 粗粒度成功/失败标记 | trajectory 判断粒度下降 |
| Final answer | 最后一个 assistant 内容，或被设计上等价的最终产物 | 必须在 spec 中说明 |
| Observation 明细 | trace 导出文件或离线重放材料 | 顺序和来源可信度下降 |

但这些“临时替代”不能由 agent 单方面采用。

要求：

- 先向用户解释替代方案的代价
- 让用户明确接受或拒绝
- 若用户同意临时硬编码或临时占位，必须标记为 `TEMP`

## 与用户讨论时可直接问的问题

- 你当前的评测项目在哪个仓库或目录？
- 相关配置文件在哪里？环境变量、judge 配置、trace 接入配置、CI 配置分别在哪？
- 新评测代码希望放进现有评测项目，还是新建目录？
- 你现在能拿到的是 Langfuse DB、API、SDK 还是导出 trace？
- 数据库配置现在能直接拿到吗？如果不能，后续是否有机会补到？
- 如果 agent 本地查不了 DB，你是愿意手动改配置去数据库验证关键字段，还是先接受风险延后验证？
- 如果 DB 走不通，你是否接受先用 SDK / API 路线？
- 如果你现在没有现成评测项目，你希望第一版用什么语言 / 框架或最小实现方式？
- 如果依赖 Langfuse，你的 project / space、鉴权方式、密钥状态、agent_name 或等价筛选字段现在都清楚吗？
- 你希望哪个模型作为默认 judge 模型？
- 是否配置一个更大上下文的兜底模型？
- 多久没有返回算超时？超时后你更希望重试、切兜底模型、降并发，还是直接失败？
- 如果没有兜底模型，你接受跳过、加强压缩，还是别的降级策略？
- 现在能恢复 prompt 名、prompt 文本，还是只能拿到最终渲染后的消息？
- tool call 和 tool result 两边都能拿到吗？
- 哪些 runtime 信息你认为应该影响评测，但目前没有上报？
- 如果 DB 一时拿不到，你是想先做 reduced-scope 第一版，还是先补 trace？

## 最终必须输出的结论

检查结束后，必须明确落在以下三类之一：

- `可以进入完整评测设计`
- `可以进入缩减版评测设计`
- `建议先补可观测性，再做评测`

同时要明确写出：

- 已确认事项
- 未确认事项
- 若 DB 本地不可查，用户最终选择了哪条路径
- 是否可以继续下一轮 discovery
- 是否已经满足进入设计 / 计划阶段的条件
