# 评测开发 Checklist

在评测设计稳定、准备开始写评测代码前使用。

- [ ] 已确认 agent 代码位置
- [ ] 已确认评测项目位置
- [ ] 已确认是否存在现成评测项目
- [ ] 若无现成项目，已完成语言 / 运行时选型
- [ ] 若无现成项目，已完成框架 / 最小实现方式选型
- [ ] 若无现成项目，已完成同仓 / 异仓策略确认
- [ ] 若无现成项目，已确认最小 runner 入口和配置承载方式
- [ ] 已确认相关配置位置（环境变量、judge 配置、trace 接入配置、CI 配置）
- [ ] 已确认新评测代码应该落在哪个目录或仓库
- [ ] 已读取原有评测项目中的可复用组件与契约
- [ ] 已确认 trace 来源是 Langfuse DB、SDK/API，还是导出文件
- [ ] 已确认当前数据获取路径是 DB、SDK/API，还是导出文件
- [ ] 已确认如果 DB 不可用，是否能补配置，或者是否改走 SDK/API
- [ ] 已确认平台关键配置（project / space、base URL、鉴权方式、keys、agent_name 或等价筛选字段）
- [ ] 已确认评测单元是 session、turn、trace 还是任务实例
- [ ] 已识别 prompt 来源
- [ ] 已识别 tool transcript 结构
- [ ] 已识别最终回答来源
- [ ] 已确认是否有 ground truth、参考答案或参考轨迹
- [ ] 已确认默认 judge 模型
- [ ] 已确认大上下文兜底模型，或已得到用户明确接受的替代策略
- [ ] 已确认模型或 judge 请求的超时阈值
- [ ] 已确认超时后的动作（重试 / 切兜底模型 / 降并发 / 失败）
- [ ] 已完成 agent 流程特色识别，并整理参考类型摘要
- [ ] 已确认 trajectory 评测范围
- [ ] 已确认 E2E 评测范围
- [ ] 已确认 RAG 维度是否纳入
- [ ] 已向用户展示平台内置 / 可复用指标
- [ ] 已完成指标推荐并得到用户确认、删除或编辑意见
- [ ] 已用简短自然语言向用户解释指标、payload、标签分别是什么
- [ ] 已确认特殊标签及边界
- [ ] 已基于现有参考标签和 agent 特性给出候选标签集合
- [ ] 已用结构化表格展示标签矩阵
- [ ] 已确认标签是否需要特别区分、合并或新增
- [ ] 已按区块检查 payload 字段来源
- [ ] 已得到用户对 payload 区块、字段可得性和 fallback 的确认
- [ ] 已完成 payload 字段映射
- [ ] 已确认 payload 高价值字段、辅助字段和条件性字段
- [ ] 已完成压缩策略
- [ ] 已确认 payload 长字段预算与超预算处理
- [ ] 已向用户简要解释指标、payload、标签推荐的理由
- [ ] 已确认正式 judge 前是否提供单条 trace 的 payload inspect / preview 入口
- [ ] 已明确 inspect / preview 至少覆盖关键字段来源、fallback、presence logging、flags 和 labels 证据链
- [ ] 已确认输出策略
- [ ] 已讨论是否需要对外暴露接口
- [ ] 若暴露接口，已确认是单条 trace 接口还是时间范围 / 条件批量接口
- [ ] 若是批量接口，已确认是否并行与并行量上限
- [ ] 只要存在批量评测执行，已确认批量执行入口、并行单位、限流方式和失败策略
- [ ] 若需要暴露接口，已在测试前告知用户测试接口与调用方式
- [ ] 已确认 readiness 阶段的未决项已经清空或被显式接受
- [ ] 若本地 DB 不可查，已显式询问用户是手动查库、带风险延后，还是改走 SDK/API/导出文件
- [ ] 若用户选择带风险继续，已明确记录未验证字段、回头验证触发条件和风险说明
- [ ] 若使用临时硬编码或临时占位，已得到用户同意并写明移除条件
- [ ] 已确认 fixture / golden trace 的来源和存放位置
- [ ] 已确认 judge 输出 schema
- [ ] 已填写评测 spec
- [ ] 已先把评测方案文档给用户查看，并得到明确确认
- [ ] 已在方案文档生成后主动告知用户文档路径、用途和建议阅读顺序
- [ ] 后续 Plan / 实现计划已明确以该方案文档为依据
- [ ] 已确认本地 / 测试环境执行方式（必要时包括 `dtools` 或等价工具）
- [ ] 已确认日志获取方式与关键日志覆盖面
- [ ] 已确认哪些关键 payload 字段需要靠运行时日志验证可得性
- [ ] 未在方案文档确认前进入 Plan / 开发
- [ ] 已先写好评测逻辑的 failing tests
- [ ] 已对 judge prompt 或 scoring code 做版本管理
- [ ] 已明确本地和 CI 的验证方式
- [ ] 已完成报错修理后的最小重跑验证
- [ ] 已抽样分析 3 到 5 条评测结果并记录是否需要优化
- [ ] 已通过轻量日志确认关键 payload 字段在运行时是拿到、为空还是缺失
- [ ] 评分异常时，已先回查 payload inspect / preview、字段来源链和 presence logging，再决定是否调整 judge
- [ ] 已完成整链路 runnable review
- [ ] 已生成并主动告知用户实现后验证文档路径、用途和建议阅读顺序
- [ ] 已明确告知用户首轮验证入口、结果落点和日志位置
- [ ] 已提醒用户先去平台官网或 trace 查看页面确认目标 trace 是否存在
- [ ] 已指导用户按 3 到 5 条代表性 trace 做首轮抽检
- [ ] 已指导用户分别检查 trajectory、e2e、标签、judge reason 和关键字段 presence 日志
- [ ] 已要求用户按结构化模板反馈问题，而不是只给模糊结论
- [ ] 已根据用户反馈中的证据决定下一轮最小优化切片
- [ ] 已根据用户反馈确定下一轮最小重跑集
- [ ] 若存在测试接口，已主动告知用户接口路径、调用方式和关键输入输出
- [ ] 若不存在测试接口，已主动告知用户当前 runner / 脚本入口

## 建议实现顺序

1. 先写 payload 提取的 failing tests
2. 再写标签推导的 failing tests
3. 再写 judge 输出解析的 failing tests
4. 再写评分输出格式的 failing tests
5. 实现 payload 组装
6. 实现标签逻辑
7. 实现评分或报告输出
8. 用代表性 trace 做验证
